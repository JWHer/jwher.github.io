# Writing Guide

블로그(`blog/`)와 문서(`docs/`) 글을 쓰거나 고칠 때의 규칙. 목표는 두 가지다:

1. **형식 통일** — front matter·마크다운 작성법을 기존 글 기준으로 일관되게.
2. **임팩트 있고 쉬운 글** — 관련 경험이 없는 사람도 이해할 수 있게.

블로그와 문서는 성격이 다르다:

| | **블로그 (`blog/`)** | **문서 (`docs/`)** |
|---|---|---|
| 목적 | 개인적 이야기·경험·느낌·관점 | 기술적으로 **검증되고 출처가 있는** 지식 |
| 목소리 | 1인칭, 주관 허용 | 중립·정확, 주장은 근거와 함께 |
| 예시 | "Claude Code로 블로그를 정비하며 배운 것" | "HyperLogLog로 distinct count 추정하기" |

---

## 1. 공통 규칙 — Front Matter

키 순서는 아래로 통일한다 (기존 글은 순서가 섞여 있으나, 새 글·수정 시 이
순서를 따른다).

### 블로그

```yaml
---
title: 'Claude Code로 블로그 대청소하기 - 100+ 글을 2시간 만에 정비한 방법'
description: Claude Code로 100+ 블로그 글을 자동 정비한 경험 - AI 기반 대규모 리팩토링의 실전 사례
slug: blog-maintenance-with-claude-code
authors:
  - jwher
tags:
  - blog
  - ai
  - claude-code
image: /img/pen.svg
draft: true          # 완성 전까지 유지, 발행 시 삭제
---
```

- **title** — 핵심을 담되 임팩트 있게. `:`나 특수문자가 들어가면 따옴표로 감싼다.
- **description** — 검색·미리보기용 한 줄 요약. title을 반복하지 말고 내용을
  압축한다 (SEO 반영 — [.claude/seo-runbook.md](.claude/seo-runbook.md) 참고).
- **slug** — 영문 kebab-case. 한 번 발행하면 바꾸지 않는다 (URL 고정). 바꿔야
  하면 `redirects.json`에 old→new 매핑 추가.
- **authors** — `blog/authors.yml`의 키(`jwher`).
- **tags** — 소문자, 기존 태그 재사용 우선(난립 방지).
- **image** — 소셜 카드/썸네일. `/img/...`(static) 또는 글 폴더 상대경로.
- **draft: true** — 미완성 글. 빌드에서 제외된다. 발행 시 이 줄을 지운다.

폴더·파일 규칙: `blog/YYYY-MM-DD-slug/index.md`, 이미지 등 자산은 같은 폴더에.

### 문서

문서 front matter는 가볍게 유지한다. `title` 없으면 첫 h1에서, `slug` 없으면
파일 경로에서 자동 생성된다.

```yaml
---
title: 'HyperLogLog: 메모리 한 줌으로 10억 개 세기'
sidebar_position: 3    # 사이드바 순서 (선택)
draft: true            # 검증 전까지 유지 (선택)
---
```

문서는 `docs/<주제>/` 아래에 둔다 (`ml/`, `cs/`, `algorithms/`,
`infrastructure/`, `development/` 등).

## 2. 공통 규칙 — 마크다운

- **제목은 `##`부터 시작.** 글 제목(h1)은 본문 바깥에서 렌더되므로, 본문 안에서는
  h2가 사실상 최상위다. 본문에 `#`(h1)을 쓰지 않는다.
  (근거: [.claude/styling-guide.md](.claude/styling-guide.md) → In-Article
  Heading Hierarchy.)
- **코드 펜스에 언어 지정** — ```` ```ts ````, ```` ```bash ````. 문법 강조·복사에
  필요.
- **순서 있는 절차는 번호 목록**, 그 외 나열은 불릿. 조건은 지시문 앞에 둔다
  ("X라면, Y하라"). *(Google 개발자 문서 스타일 가이드)*
- **링크 텍스트는 서술적으로.** "[여기](...)" 대신 "[Diátaxis 프레임워크](...)".
- **이미지에는 alt 텍스트.** 원본 크기로 업로드하고 모양은 CSS로 조정한다
  (재업로드 방지 — styling-guide 참고).
- **표**는 비교·스펙에만. 서술로 충분하면 표로 만들지 않는다.

## 3. 내용 — 톤과 전달

핵심 원칙: **임팩트 있고, 초등학생도 알아들을 수 있게.** 전문용어를 금지하는 게
아니라, **익숙하지 않은 개념은 비유로 직관을 먼저 심고** 정확한 용어를 붙인다.

- **임팩트 먼저.** 추상적 정의가 아니라 구체적 사건·숫자·이해관계로 연다.
  ("YouTube는 하루 방문자 수를 어떻게 셀까?" > "카디널리티 추정이란…")
- **어려운 개념 = 비유 + 정확한 용어.** 비유로 그림을 그린 뒤 정식 명칭을 준다.
  예: "확률적 카운터는 *양동이에 빗방울 몇 개 떨어졌나로 비 온 시간을 어림하는*
  것과 같다 — 이것이 **HyperLogLog**다."
- **능동태·현재형·직접 화법.** "~된다" 남발 대신 주어를 드러낸다. 독자를
  "여러분/당신"으로 직접 부른다. *(Google 스타일 가이드)*
- **구체 > 재치.** 모호하거나 멋부린 표현보다 정확한 단어. 같은 개념은 글 전체에서
  같은 단어로 부른다 (용어 흔들지 않기).
- **문서는 출처를 단다.** 수치·주장에는 논문·공식 문서 링크. 확인 전이면 `draft`.

## 4. 권장 글 구조

기술 글은 아래 5단계 흐름을 권장한다. 독자를 "왜 필요한지"부터 데려가
"실제로 쓰이는 곳"에서 내려놓는다.

| 섹션 | 역할 | 예시 (Distinct Count / HyperLogLog) |
|---|---|---|
| **Hook** | 현실감 있는 사례로 문제를 체감시킨다 | YouTube 고유 방문자 수 — "10억 개를 어떻게 세지?" (메모리 한계의 현실감) |
| **필요성** | 왜 순진한 방법이 안 되는지 → 새 접근의 동기 | 세 가지 대규모 데이터 문제 → 스트리밍 모델 선택 |
| **도구** | 해결에 필요한 개념·재료를 먼저 깐다 | 확률적 분석에 필요한 부등식 계층 |
| **해결** | 문제를 단계별로 실제로 푼다 | Distinct Element 문제를 단계별로 풀기 |
| **결과** | 실제 시스템·제품과 연결해 착지 | HyperLogLog → Redis, BigQuery 실사용 연결 |

- 모든 글이 5단계를 다 갖출 필요는 없지만, **Hook과 결과(착지)는 거의 항상 필요**하다.
- 블로그는 여기에 개인 경험·감상을 얹고, 문서는 각 단계를 검증·인용으로 받친다.

### 참고: Diátaxis (문서 유형 분리)

문서를 쓸 때는 한 글에 성격을 섞지 않는다 *(Diátaxis 프레임워크)*:

- **Tutorial** — 배우는 사람을 위한 손잡고 따라하기
- **How-to** — 특정 작업 목표 달성 절차
- **Reference** — 사실·스펙 나열
- **Explanation** — 개념·배경·"왜"의 이해

튜토리얼에 레퍼런스를 쏟아붓거나 how-to에 개념 설명을 끼우면 둘 다 약해진다.
글 하나의 유형을 먼저 정하고 거기 집중한다.

## 5. 발행 전 체크리스트

- [ ] front matter: 순서·필수 키 확인, `draft` 정리
- [ ] 본문 제목이 `##`부터 시작하는가
- [ ] Hook이 구체적 사례/숫자로 시작하는가
- [ ] 어려운 개념마다 비유로 직관을 먼저 주었는가
- [ ] (문서) 수치·주장에 출처 링크가 있는가
- [ ] 코드 펜스에 언어가 지정됐는가, 이미지에 alt가 있는가
- [ ] `npm run build` 통과 (MDX 문법 오류 없음)
